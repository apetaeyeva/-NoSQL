## 5. Анализ RPO / RTO
- **Наблюдаемое RTO** = t1 − t0 = ‹…› с. Для записи клиентом добавьте интервал от t0 до первого ACK после FAIL в `probe.log`: ‹…› с.
- **Проверка потери данных (RPO):** последний ACK в `probe.log` до отказа = ‹…›; после отказа `06_check_after.js` показывает max probeId = ‹…›, gaps = ‹…›. Все подтверждённые (ACK с w:majority) записи ‹сохранены / не сохранены›. FAIL-записи не считаются потерянными подтверждёнными данными: клиент знал, что запись не подтверждена.
- Успешный failover сам по себе не доказывает RPO = 0; вывод делается только по сравнению контрольных записей.
- **Проектные допущения (целевые значения для журнала оценок):** RPO ≤ ‹0 для подтверждённых оценок (w:majority) / ≤ 5 мин для резервной копии›, RTO ≤ ‹30 с для автоматического failover; ≤ 1 ч для восстановления из backup›. Обоснование: оценка студента юридически значимая запись, её потеря недопустима, а кратковременная недоступность записи (секунды) приемлема.

## 9. Ответы на контрольные вопросы (кратко)
1. Репликация поддерживает копии для доступности, но реплицирует и ошибочные удаления; backup даёт точку во времени для отката.
2. Кворум (большинство голосов) нужен, чтобы в разделённой сети не появилось два primary (split brain).
3. Primary принимает обычные операции записи, ведёт oplog; secondary его воспроизводят.
4. При потере большинства голосов нового primary не выбрать; оставшиеся узлы остаются SECONDARY, запись невозможна, чтение возможно только с подходящим read preference.
5. w:majority защищает от потери подтверждённой записи при failover, но не от логических ошибок (удаление, порча данных), потери всего кластера и т. п.
6. t1 − t0 по логам или наблюдателю: от остановки primary до появления нового PRIMARY.
7. RPO: допустимая потеря данных во времени; RTO: допустимое время восстановления работы.
8. Чтобы ошибка восстановления не затёрла рабочие данные и можно было сравнить результат с оригиналом.
9. Кратковременная недоступность записи, ошибки в клиентах, незавершённые операции; риск потери большинства при остановке второго узла.
10. Одна машина, нет сетевых и дисковых сбоев, малая нагрузка, нет аутентификации и TLS, нет географического распределения.
